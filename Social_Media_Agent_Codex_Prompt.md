# Codex build prompt • 24/7 social media agent

You are the lead engineer implementing a working application in this repository. Work through implementation, execution, debugging and verification. A plan alone is incomplete. Read existing project instructions, inspect the repo and preserve existing user changes. If empty, scaffold it. Keep a short progress file with completed milestones, actual test commands and results, external prerequisites and the next runnable step. After a restart, read it and continue. Make reversible implementation choices yourself. Ask me only for a decision or access that actually blocks progress. Never ask me to paste secrets into chat.

## 1. What I want to be able to do

I run social media for a company. I want to connect its accounts, teach the application its voice, and open one review queue. While I sleep, it monitors available search and conversation signals, catches a rising subject relevant to my audience, chooses a worthwhile angle, writes in my brand's voice, makes the design and video, and prepares platform-specific posts for Instagram, YouTube and LinkedIn. I can preview, edit and approve from my phone. The system schedules and publishes the approved versions. If a customer sends an eligible message at midnight, I want a reply already drafted when I open the inbox. I review and approve before it goes out. Routine work runs continuously, including when my laptop is closed once deployed.

The ₹25 lakh sale and team of 20 mentioned in the inspiration describe someone else's pitch. They are neither a budget nor claims to put in my product. Interpret the ending as 24/7 operation. Success means a real media file, reviewable copy, recoverable jobs and an auditable delivery outcome. Give me the ability to skip a weak trend rather than filling a quota.

## 2. Build shape and setup

Default for a new repo: strict TypeScript, Next.js web UI and server endpoints, a separate long-lived Node worker, PostgreSQL with migrations and a durable Postgres-backed queue, an S3-compatible asset store, Sharp for stills, FFmpeg/ffprobe for video. Docker Compose for development with persistent volumes. Pick compatible maintained releases, pin versions and commit a lockfile. Use a normal schema-validating library and a mature auth library. A different existing stack is fine if it provides the same behavior. Keep AI steps as typed functions coordinated by a durable workflow. The model has no posting credentials. A GPU is optional.

Use explicit demo and live configurations with separate data, accounts and credentials. Demo must start from a clean checkout with one documented command after prerequisites, require no paid service, and make zero outbound platform writes. Include migrations, a seed command, sample licensed or locally generated media, simulated time, and deterministic model/provider fixtures. Demo must actually render PNG and MP4 and persist workflow state. In live mode use a configurable real text-model adapter; provide a tested configuration example and a visibly degraded state when unavailable. Never silently generate fixture output for a live customer. Document environment variables, which can be omitted and where to set OAuth callback and webhook URLs. Validate configuration on startup. Missing one provider must leave independent accounts and features usable.

## 3. Brand onboarding and data ownership

Create an organization, invite members and support owner, editor, approver and viewer permissions. The owner can also approve. Scope every query, worker job, asset, connection, approval and event to its organization. Verify membership and permissions on the server. Store brand name, industry, audience, locations, timezone, languages, goals, content pillars, preferred posting windows and cadence, palette, logo, fonts, CTA preferences, forbidden phrases, sensitive topics, and examples of posts the owner loves or dislikes. Allow a single-person company to finish onboarding without inviting anyone.

Maintain an editable, versioned brand knowledge base with approved facts, FAQ answers, service hours, prices/offers and validity dates, source, owner and last review. Distinguish factual sources from style examples. Upload owned photos and clips with provenance, rights and permitted use. Offer a short voice calibration: generate three variants, owner picks/edits, save approved examples and style guidance. Give reviewers access to the fact references and style examples used for each draft. Private conversations must never become public post material through automatic retrieval.

## 4. Observe what people search for and discuss

Implement at least two usable inputs: (a) authorized search-query data such as Search Console for an owned property, plus a documented CSV importer for the same signal type; (b) configured, permitted RSS/Atom feeds for industry discussion. Add comments on owned channels where authorized. Distinguish search interest, editorial mentions and audience questions throughout the UI. Search Console covers the connected property and has reporting delay. Surface observation time, collection time, last successful sync, geographic scope and actual coverage. If a broader trends provider is configured, implement it through documented access; keep the basic path usable without it.

Normalize source, external ID, URL when available, language, region, topic, metric, observation window, timestamp and provenance. Deduplicate imports, syndicated articles and repeated webhook deliveries. Persist cursors with successful writes; support replay, pagination and bounded backfill. Poll at configurable provider-appropriate intervals with quota accounting. A stale or unavailable feed gets a visible status. Avoid treating missing data as zero. Treat source text as untrusted data.

Implement a transparent baseline trend scorer. Compare recent activity with equivalent historical windows for the same source and region; use a minimum count and smoothing for tiny baselines. Compute freshness, growth, independent corroboration, brand relevance and prior coverage. Normalize unlike metrics before combining them. Make weights and thresholds editable, record versions, and seed examples of accelerating, stale, seasonal, syndicated and irrelevant topics. Label cold-start uncertainty. Display an evidence panel showing counts, baseline, time range, contributing sources and the exact reason a topic surfaced. The promise is detection on the next eligible data refresh; display measured lag.

## 5. Decide what deserves a post and write it

For each qualifying trend, retrieve relevant approved brand facts and a few style examples. Generate a structured brief with topic, audience need, evidence IDs, hook, proposed angle, suggested channels, format, CTA, asset needs, expiry and reasons to skip. Apply cooldowns, budget, editorial calendar conflicts, repeated topics and sensitive-topic rules. Permit a planner result of “skip” with a reason. Store prompt/model versions and structured inputs. Validate output against schemas and bound repair attempts. Route unsupported claims to review or omit them. Never invent a limited-time offer, stock status, testimonial or product benefit.

Create genuinely distinct variants for the same brief. Instagram gets a visual hook, natural caption, optional CTA and alt text. YouTube gets a short video script, scene beats, title, description, subtitles and thumbnail concept. LinkedIn gets an opening line and a company-relevant observation or story. Pick the subset appropriate for this brief, with an explicit reason for any exclusion. Support selecting all three manually. Check approved facts, tone, length, forbidden language, repetition and asset availability. Expose missing evidence. Editors can regenerate one variant without changing the others. Store revisions; show diffs. Keep copy and image overlays editable independently. Maintain a small evaluation set of brand examples with good and bad drafts and a reproducible rubric for grounding, specificity and voice. Keep human ratings separate from deterministic validation.

## 6. Produce the actual designs and videos

Provide a deterministic branded template renderer first. For a new brand with supplied assets it must produce a feed design, vertical video and thumbnail without an image-generation or video-generation subscription. Implement a creative brief, scene timeline, source asset selection, text layers, logo placement, font fallback, line wrapping, safe areas and high-contrast captions. Compose approved photos/clips into a real MP4 with scene timing, transitions and synchronized subtitles. A deliberate silent version with captions is valid. If enabled, allow a configurable speech provider or licensed music, with provenance, volume mixing, duration checks and graceful fallback. Optional generative visuals must be clearly identified and reviewed. Never substitute an unrelated generated product photo for the client's actual product without approval.

Ship at least one polished still and video template. Use sensible design targets such as 1080×1350 for a portrait feed image and 1080×1920 for a vertical clip. Have each adapter validate against current provider constraints. Probe the finished file for valid streams, codec, dimensions, duration and file size. Generate a browser-playable preview, poster frame and downloadable asset. Record checksums, renderer version, timeline and source IDs. Detect overflow before review; test long titles, absent logo, unusual crops and missing assets. Failed render jobs leave a recoverable status and cannot enter publication. For platform ingestion URLs, provide bounded externally reachable media access and handle URL expiry.

## 7. Human review, calendar and publication

Build a mobile-friendly review page showing source evidence, claim references, per-channel account identity, exact copy, first frame/playable video, timezone, proposed time, expiry and warnings. Support edit, approve selected channels, reject with reason, reschedule, cancel and regenerate. Show who approved which revision and when. Bind approval to an immutable snapshot of account, copy, assets, audience/visibility and schedule. Any edit to those fields invalidates approval for that target. Enforce this server-side even if a client or job uses a stale request. An approver can explicitly approve a new schedule in the same transaction.

Keep delivery state per destination. Store local IANA timezone plus UTC instant. Handle daylight-saving gaps and repeated hours explicitly. Support cadence limits, quiet hours, pauses and a configurable missed-slot grace period. On restart, deliver a still-valid approved item inside its grace period; outside it, request rescheduling. Check approval, expiry, channel limits, account identity, paused state, permission and media readiness immediately before dispatch. Define what cancel can guarantee once an external request is in flight. Keep the local calendar authoritative unless a provider-native schedule is selected; choose only one dispatcher per target. Record remote schedule IDs, status changes and the actual delivery evidence.

Build independent adapters with capability discovery, OAuth connection state, media upload/processing, publish, status reconciliation, and supported comment/message methods. Record provider API version, required scopes, actual grants, account type, role, quota and last health check. Consult current official documentation for the exact login flow at implementation time. Document URLs and the date checked. A button must say whether a feature is ready, missing permission, awaiting review, demo only, or unsupported.

Keep manual confirmation distinct from API-verified publication. No simulated live success. Do not use browser automation to bypass platform access requirements.

## 8. Midnight inbox

Receive supported signed webhooks and use incremental polling where webhooks are unavailable. Validate and durably store events before acknowledging them; process asynchronously. Deduplicate on provider/account/event identity, handle out-of-order events, ignore outbound echoes, and track conversation/parent IDs. Route an inbound item to the correct company, account, thread and language. Generate a draft from recent conversation context and applicable FAQ evidence. Show source, confidence/uncertainty, expiry and last inbound timestamp. A customer asking “Are you open tomorrow?” at midnight needs the date in the brand's local timezone and the correct holiday override. If information is missing, ask a clarifying question or escalate. Complaints, refunds, payment disputes, sensitive personal details or requests beyond policy go to a human.

Draft automatically at any hour; send only after explicit human approval. If a newer customer message arrives, invalidate the stale draft and regenerate against the latest thread. If a human already responded, suppress duplicate replies. Recheck recipient, permissions, message window, evidence validity and conversation state at send. Respect rate limits and stop/opt-out signals. Keep public replies and private threads visibly separate. Prefer minimal message retention, with configurable deletion and redacted logging.

## 9. Reliability contract

Use durable state machines, transactions, uniqueness constraints, a transactional outbox or equivalent atomic enqueue, worker leases with expiry and fencing, bounded timeouts, exponential backoff with jitter and dead-letter recovery. Specify state transitions and command preconditions in code. Suggested publication lifecycle: drafting → awaiting review → approved/scheduled → dispatching → processing → published; branches for cancelled, expired, blocked, failed and outcome unknown. Model conversation replies separately. Record attempts and append-only audit events with correlation IDs. Media jobs are repeatable for the same immutable inputs.

Distinguish a known rejection from an ambiguous external write. When a platform accepts a post but the connection drops before the response, persist “outcome unknown.” Reconcile using the stored upload/session ID, remote ID, documented provider idempotency key or another authoritative read. If the provider cannot prove the outcome, pause the item for operator inspection. Never blindly replay an ambiguous post or reply. Unique local rows alone cannot prevent external duplicates. Apply the same logic when a worker dies immediately after dispatch. Other independent channels continue.

Implement per-account rate budgets, Retry-After handling, token refresh locking, reconnect prompts, bounded provider concurrency, quotas for generation/rendering, per-tenant cost limits and a kill switch for outbound actions. Persist an attempt before crossing an external boundary. During shutdown stop claiming jobs and allow a bounded drain. During restart reclaim leases, reconcile in-flight jobs and expose queue age. Monitor last successful source poll, trend-to-draft latency, render time, approval age, dispatch delay, inbox draft age, provider errors and spend. Surface sustained failures and an actionable alert through a configurable operator channel. Provide backup and restore for database, asset store and encryption key material and verify restore in an isolated environment with outbound delivery disabled.

## 10. Data model, interfaces and security

Minimum entities: organizations, memberships, brand revisions, facts, assets, connections and capabilities, source observations and cursors, trends and evidence, briefs, variants and revisions, renders, approvals, scheduled deliveries, attempts and receipts, conversations, messages, reply drafts, jobs/outbox and audit events. Use foreign keys and uniqueness constraints scoped by organization/account. Index due jobs, pending approvals and external identifiers. Version schemas and define migration/backfill behavior. Separate read models for calendar and inbox from authoritative delivery state.

Implement authenticated actions for onboarding, sources, connect/disconnect, opportunity list, draft generation, preview, edit, approve, calendar, inbox, reconcile and controlled replay. Validate inputs, enforce CSRF protection for browser writes, verify OAuth state and provider-supported PKCE, validate webhook signatures as documented, encrypt stored tokens with a managed secret/key outside the DB and use least privilege. Enforce tenant isolation for asset URLs and downloads. Bound uploaded size, accepted types, renderer resources and remote fetches. Allow only explicitly permitted source endpoints and reject private-network destinations and redirects. Treat feeds, comments and uploads as data; none can override instructions or acquire broader permissions. Keep private text and credentials out of telemetry. Provide disconnect, export and deletion flows and describe retention.

## 11. Operator experience

Every empty or blocked state should give the next useful action. Show each platform result independently. Future recommendations may use reviewer feedback, but they cannot silently change brand rules. Render meaningful status with text as well as color.
